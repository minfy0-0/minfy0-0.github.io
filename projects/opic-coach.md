## 01. 문제 정의 — 답안 생성이 아니라 연습 흐름 자체를 개선하기

OPIc를 준비하면서 질문 자료, 개인 스크립트, 실제 말하기, 피드백, 연습 기록이 서로 분리되어 있어 매번 여러 도구를 오가야 했습니다. 단순히 AI가 답안을 만들어 주는 서비스보다 **질문을 듣고 직접 말한 뒤, 왜 점수가 낮은지 이해하고 다시 연습할 수 있는 흐름**이 더 필요했습니다.

그래서 처음부터 기능 개수보다 실제 학습 순서를 기준으로 제품 구조를 잡았습니다.

1. 공용 문제은행에서 주제 선택
2. 실전 모드 / 암기 모드 선택
3. 기준 스크립트 없이 연습하거나 내 스크립트 불러오기
4. 질문을 화면에 노출하지 않고 음성으로 듣기
5. 사용자가 직접 RECORD / STOP으로 답변 녹음
6. Whisper로 음성을 전사하고 필요한 경우 직접 수정
7. 세분화된 AI 피드백 확인
8. 로그인 사용자의 스크립트·연습 기록 누적

이후 실제 사용 과정에서 발견한 문제를 기준으로 **모의고사, 다크 모드, 마이크 테스트, 한국어 피드백 보정, 인증 UX**까지 계속 확장했습니다.

## 02. 문제은행 — 공용 콘텐츠와 개인 데이터를 분리

현재 공용 문제은행에는 **74개 활성 주제와 264개 활성 질문 변형**이 연결되어 있습니다. 질문은 주제별 여러 variant로 구성해 같은 주제를 반복하더라도 완전히 같은 문장만 나오지 않도록 했습니다.

데이터는 다음처럼 역할에 따라 분리했습니다.

- `topics` — 공용 문제 주제
- `questions` — 공용 질문 변형
- `scripts` — 로그인 사용자별 개인 스크립트
- `practice_records` — 사용자별 전사·피드백·연습 기록
- `profiles` — 사용자 프로필 / 닉네임

공용 문제은행은 게스트도 사용할 수 있지만, 개인 데이터는 **Supabase Auth + Postgres + Row Level Security**로 본인 데이터만 접근하도록 구성했습니다. 이메일 로그인뿐 아니라 카카오 로그인도 추가했고, 로그인하지 않은 사용자는 게스트 모드로 바로 연습할 수 있게 했습니다.

## 03. 일반 연습 — 시험처럼 듣고, 실제로 말하도록

질문은 텍스트를 먼저 보여주지 않고 음성으로 제공합니다. 운영 질문 음성은 **Hannah voice**로 고정했고, 사용자는 최대 2회까지 질문을 들을 수 있습니다.

연습 전에 브라우저 마이크가 정상적으로 동작하는지 확인할 수 있도록 별도의 **Mic Check**도 추가했습니다. 입력 레벨을 실시간으로 보여주고 짧게 녹음한 목소리를 다시 들을 수 있어, 실제 연습 전에 권한·입력장치 문제를 확인할 수 있습니다.

답변 녹음 후에는 **Whisper Large V3 Turbo**로 전사합니다. 자동 전사 결과가 완벽하지 않을 수 있으므로 AI 피드백 전에 사용자가 텍스트를 직접 수정할 수 있게 했습니다.

## 04. 배경 설문 기반 모의고사 — 단순 랜덤이 아닌 OPIc 조합 구조

초기에는 문제를 단순 랜덤으로 조합했지만 실제 시험의 흐름과 거리가 있었습니다. 이후 모의고사 구조를 다시 설계해 **배경 설문 주제 → 돌발 → 롤플레이 → 어드밴스** 조합으로 문제를 구성하도록 개선했습니다.

### Survey combo

사용자가 선택한 배경 설문 주제를 바탕으로 같은 주제 안에서 다음 3문제 흐름을 우선 구성합니다.

- 묘사
- 루틴·습관
- 경험

카페, 공원, 해변, 음악·콘서트, 술집·바, 조깅·걷기, 집, 여행, 쇼핑, 집에서 보내는 휴가 등의 주제를 현재 문제은행과 연결했습니다.

### Surprise combo

배경 설문 외 돌발 주제도 별도 family로 구성했습니다. 현재 날씨, 인터넷, 은행, 재활용, 음식점 등의 주제를 묘사·루틴·경험 흐름으로 조합합니다.

### Roleplay 11–13

롤플레이는 한 문제씩 무작위로 섞기보다 하나의 상황을 기준으로 연결합니다.

- 11번: 정보 요청
- 12번: 문제 해결
- 13번: 비슷한 과거 경험

공원 약속, 쇼핑 약속, 콘서트, 집 수리, 여행·호텔, 은행 등의 상황을 같은 family로 묶었습니다.

### Advance 14–15

비교, 변화, 이슈, 해결책 등 상대적으로 복합적인 주제를 별도로 분리하고 질문의 시간 조건에 맞춰 **현재·과거·현재완료 중 어떤 시제를 우선해야 하는지** 힌트를 함께 설계했습니다.

모의고사는 개인 연습보다 비용과 기록 관리가 더 큰 기능이어서 **로그인 사용자에게만 노출**하도록 UX도 조정했습니다.

## 05. AI 피드백 — “몇 점”보다 “왜 그 점수인지”가 보이도록

초기 버전에서는 문법 점수가 낮게 나와도 이유가 충분히 보이지 않거나, 설명 일부가 영어로 출력되는 문제가 있었습니다. 이 부분을 가장 크게 수정했습니다.

현재 피드백은 기본적으로 다음 4축을 각각 0–100점으로 평가합니다.

| Metric | 보는 기준 |
| --- | --- |
| Question relevance | 질문의 핵심 요구에 직접 답했는지 |
| Naturalness | 답변 흐름과 말하기 자연스러움 |
| Grammar | 의미 전달에 영향을 주는 문법·동사·문장 구조 |
| Tense control | 질문에 필요한 시제를 선택하고 유지했는지 |

점수만 보여주지 않고 각 항목별 **score reason**을 함께 제공합니다. 문법 피드백은 단순 철자 차이가 아니라 실제 말하기에 영향을 주는 문제를 중심으로 최대 3개의 `Grammar Issue`를 정리하고, 각각 원문·수정문·이유를 제공합니다.

시제는 별도 분석 영역으로 분리해 다음을 보여줍니다.

- 질문에서 기대되는 시제
- 실제 답변의 시제 사용 결과
- 잘 사용한 예시
- 수정하면 좋은 문장

추가로 답변 강점, 우선 개선 포인트, flow notes, OPIc tips를 제공합니다.

### 기준 스크립트가 있을 때

스크립트를 선택한 경우에는 일반 평가 외에도 다음 항목을 추가합니다.

- Script match
- Content coverage
- 맞게 재현한 내용
- 빠진 핵심 내용
- 자연스럽게 paraphrase한 표현
- 스크립트와 실제 답변의 matched / paraphrase / missing 비교

즉, 암기 모드에서도 “원문과 똑같이 말했는가”만 보는 것이 아니라 **핵심을 유지하면서 자연스럽게 바꿔 말한 부분**을 구분해 확인할 수 있도록 했습니다.

## 06. 한국어 피드백 보정 — 모델 출력 문제를 제품 로직에서 처리

피드백 모델은 현재 **GPT-OSS-120B**를 사용합니다. 다만 프롬프트만으로는 일부 설명이 영어로 나오는 경우가 있어, 응답을 받은 뒤 한국어가 필요한 필드를 검사하는 로직을 추가했습니다.

한국어 설명이 빠진 경우에는 별도의 repair prompt를 한 번 더 호출하고, 그래도 문제가 있으면 서비스 코드의 한국어 fallback 문구를 사용합니다. 이 방식으로 **모델의 출력 불안정성을 UI에 그대로 노출하지 않도록** 했습니다.

또한 5점 척도처럼 잘못 반환된 점수도 100점 척도로 정규화하고, 실제 발음이 같은 단순 표기 차이는 문법 오류 목록에서 제외하는 후처리를 추가했습니다.

## 07. 사용성 개선 — 실제 사용하면서 반복 수정

최근에는 AI 기능뿐 아니라 서비스 자체의 사용성을 계속 손봤습니다.

- Light / Dark mode 제공
- 다크 모드 하단 배경까지 일관되게 보이도록 테마 수정
- 문제은행 로딩 실패 시 재시도 로직 추가
- 이메일 인증 메시지와 주요 인증 오류를 한국어 UX 문구로 변환
- 카카오 로그인 추가
- 사용자별 랜덤 닉네임 및 닉네임 수정
- 게스트는 빠르게 연습, 로그인 사용자는 기록과 스크립트 저장
- Dashboard에서 누적 연습, 평균 질문 적합도, 평균 문법, 저장 스크립트 수 확인

이 프로젝트는 한 번 완성한 뒤 끝낸 것이 아니라, 실제로 제가 계속 사용하는 서비스라서 **불편을 발견 → 원인 확인 → UI/프롬프트/데이터 구조 수정 → 다시 사용**하는 방식으로 발전시키고 있습니다.

## 09. 이 프로젝트에서 보여주는 역량

이 프로젝트의 핵심은 AI API를 연결한 것 자체가 아닙니다.

**사용자 문제 정의 → 문제은행/개인 데이터 구조 설계 → 시험 구조를 반영한 모의고사 로직 → 음성·LLM 파이프라인 → 실제 사용 피드백을 통한 반복 개선**까지 하나의 제품 흐름을 직접 설계했다는 점에 의미가 있습니다.

특히 피드백의 언어 오류나 점수 설명 부족처럼 실제 사용 중 드러난 품질 문제를 프롬프트 수정만으로 끝내지 않고, 검증·repair·fallback 로직까지 추가해 제품 수준에서 다룬 경험을 정리했습니다.
